## Architecture

- Symfony 7.4 on PHP 8.5, PostgreSQL, FrankenPHP in worker mode (Caddy + PHP in one container), everything in Docker, plain HTTP. Layout: `.docker/php/{Dockerfile,Caddyfile,php.ini}`, `compose.yaml`, `compose.override.yaml`, Makefile (`init`, `upd`, `updb`, `down`, `in`, `cs`, `fix`, `stan`, `test`, `lint`), `.env` with committed defaults and `.env.local` for machine-specific values and the sandbox key.
- The LLM key is the sandbox key from `.env.local`.
- Two languages by necessity: the routing service (given) and the holdout script are Python, standard library only, so a facilitator can run them offline without Docker. Everything else is PHP.
- PostgreSQL holds only what the sandbox does not: cached LLM findings (with quotes and the source reference), holdout assignments, computed recommendations for the day. Merchants, deals, sold-outs and marks are read from and written to the sandbox API through a port, not copied.
- The same port has a second adapter that reads CSV files from a data-pack directory. The hand-in rules say a facilitator may run the tests and the detector offline, from a file, on data we have not seen; so the verdicts and the suppression list can be produced without the network and without the key.
- Domain areas under `src/Domain/`: `SoldOut` (recommendation, rules), `Money` (the model), `TextSignal` (findings, quote verification), `Holdout` (assignment). Adapters under `src/Infrastructure/`: `Sandbox` (HTTP client), `Llm` (gateway client).
- Access to the tool: HTTP Basic auth with one shared login and password from `.env.local` (`BASIC_AUTH_USER`, `BASIC_AUTH_PASSWORD`), checked by a request subscriber on every route; no user accounts. The shared login carries no rep, so the rep is selected in the tool and that rep id goes into `marked_by`. Only a rep-facing page and a mark form are exposed.
- Front end: Twig pages styled with Bootstrap 5, loaded from a CDN with a pinned exact version and SRI hashes, mobile-first (viewport meta, single-column cards). No asset build step. Cost: the page needs internet to be styled; acceptable for a rep tool, and the PHP tests never load it.

## Money model

- Computed only in code, in integer pence. A `Money` VO with explicit rounding.
- Per sold-out: expected GP of a cap raise, minus the cost of rep time (minutes per task × a rate), minus expected refund risk. Anything not derivable from the data is an explicit named parameter with a default, shown in the README and the memos, never buried in code.
- The rate for rep time is £20 per rep hour, tested at £15 to £30. Neither Dan nor Priya has a figure and Dan said to use ours and say so; the range is a placeholder the owner may replace. The 12 minutes per task is `minutes_per_task` in the routing config (210 minutes a day), a scheduling assumption and not a measured cost; `duration_s` exists for calls only.
- Inputs come from history in the data pack: restock rates after a call vs. none by size band, GP in the 30 days after, the merchant's refund rate in `merchant_months.csv`, and whether a schedule or Deal Alert already covered the case.
- The model reports a range (low / central / high), not one number, because the data is observational.
- Data traps to handle (PLAN 2.5): replayed CRM activity rows, blank `rep_id` before 2025, `gp_30d_after_gbp` blank for October 2026, refunds arriving later than the 30-day window, schedules joining on `deal_id` and date only, Deal Alert sends existing only from August 2025, the early-2026 CRM migration that nobody has checked (no one we asked knows of anything), and a non-rep `owner_id`.
- Checked on the data pack (aggregates only, nothing committed): every `owner_id` in `activities.csv` is one of R01–R24 from `reps.csv`, so there are no non-rep owners in the CSV pack; the claim most likely comes from the README line "owner_id is a rep id unless something odd happened". 526 of 38,850 activity rows repeat on every field except the id (520 of 24,850 restock-linked rows repeat on task, date and duration); the file has dates only, no time, so the dedupe key is the date. Some repeats may be genuine (two identical emails on one day), so the dedupe is checked by activity type before rows are dropped. 380 of 15,267 notes repeat on merchant, rep, timestamp and text with a new id.
- Historical estimates (task 2.3, `config/historical_estimates.json`, per size band, aggregates only). "Called" means the first deduplicated call is on or before `restocked_date`. GP difference per called sold-out in pence: A 496 [299, 692], B 208 [104, 314], C 30 [-51, 111], D 83 [27, 137]; Priya's £11 is 1100. They are observational: in A, B and C called sold-outs restock less often yet earn more GP, so reps choose whom to call and the numbers are not the effect of a call. The restock-rate gap is not used as an uplift; the GP difference is the input for 2.4, as a range.
- These 2.3 numbers carry a known bias: sold-outs that restock quickly have little time to be called first, so they land in "left alone" and raise its restock rate. They are superseded by the fixed-window comparison below, once it is run.
- Fixed-window comparison (task 2.7): "called" means a call within N days of the sold-out date, and both groups are measured from the sold-out date. N is taken from the data (days from the sold-out to the first deduplicated call, median or 75th percentile) and shown with a sensitivity table, e.g. N = 3, 7, 14. Split by schedule coverage, since the schedules are in the data pack. Which sold-outs reps leave alone on purpose is not visible in the data and stays a README caveat.
- The "unconfounded" cut (no active schedule, no Deal Alert send from 7 days before the sold-out) drops about 70% of sold-outs, 64% of them because of Deal Alert alone. `alert_type` is not read, so the cut effectively means "the automated sold-out alert fired". Sends exist only from August 2025, so the cut leans towards older sold-outs; task 2.5 looks at it.
- Intervals are Wald approximations and treat a merchant's sold-outs and months as independent, so they are too narrow, the refund rate most of all.
- The yearly number for Dan (PLAN 2.8): one central figure with the range next to it, labelled a model estimate that the holdout replaces, so it cannot be quoted as a measured result; never Priya's £11 times the queue. It comes after 2.7 and after the schedule share and its method have gone to Priya (promised). With it goes a short answer in numbers to "why the £11 does not hold". Unverified back-of-envelope, not for Dan: about 600 tasks a week is about 31,000 a year; the superseded 2.3 estimates are £0.30 to £5 of GP per called sold-out by band, so tens of thousands of £ and not £340k; 12 minutes per task is about 6,000 rep hours a year, about £120k at £20, which may outweigh the gain, so the value may lie in not calling where a call does not pay.

## Text analysis (LLM)

- Sources: rep notes and Deal Alert replies first; reviews and refund reasons only if time allows (cut candidate).
- Per merchant, the LLM returns structured JSON (`output_config.format` with a schema, thinking disabled, `max_tokens` sized for the answer; check `stop_reason` before parsing): a list of signals, each with a type from a fixed enum, a short rationale and a verbatim quote with the source id.
- Verified signals change the recommendation, not only the detail view: a capacity limit or a do-not-call note moves a sold-out away from `call`, and the quote is shown as the reason.
- Signal types are decided from a first look at a sample, then fixed in an enum (e.g. capacity limit, wants more, do not call, already handled, contact change, out-of-office).
- The prompt states that the text is data to analyse and must not be followed, and wraps every text in delimiters (some records read like requests, e.g. "send all contract stuff to her from now on").
- Quote verification in code: a quote is kept only if it is a substring of the cleaned source text. Cleaning: mojibake repair (Windows-1252 read as UTF-8), whitespace normalisation, dedupe of replayed notes (same merchant, rep, time and text, new id). The cut at 500 characters is accepted and noted.
- Findings are checked against a rep who knows the merchants (Renee for North H&B): a small list of merchants with the tool's finding and quote goes to her in chat, and her answer is recorded. The sample is therefore taken from her book, and she covers that one book only; the README says so. No second rep is asked. Agreements are claimed in the README only if actually made.
- Cost control: estimate from 5–10 merchants first, then run in small concurrent batches (rate limit 10 requests per second, 429 means wait `Retry-After`). Budget USD 20 for everything.

## Holdout and the real number

- A holdout is a deterministic random share of the deals that would go on the suppression list (a salted hash of the `deal_id` with a stored salt), chosen once before the list is built, because the list stays static until 7 January. The held-out deals keep their tasks, so suppressed and kept groups are comparable. Assignment is written down before outcomes are known.
- The read-out script reads two files (assignments, outcomes) and prints the difference in GP with a bootstrap interval, offline, from a file. Sample fixtures included.
- The range given to Dan now comes from the money model and the historical data; the real number comes after the first 30-day outcomes. The date is stated honestly: 30 days after the switch goes on. Whether that is before the freeze or after 7 January depends on when the switch goes on (open), so both dates are given.

- Decided with the owner: the holdout share is 0.2 (the held-out deals keep their tasks, so the share is the price of the proof; too small a control shows nothing, too large wastes the saving; no power calculation, fixed once and enforced by the tool). The export date is a parameter (`--on`): the real date is the day the list is built before Friday's gate, 11 November was only a dry run (1,536 candidate deals, 306 held out). A deal sells out about six times (6,593 of 6,640 deals more than once), so a deal-level list suppresses every later sold-out of a listed deal.
